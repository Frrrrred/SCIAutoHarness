# Recovery and semantic maintenance

Resume an existing supplied task by reading only master and recovery, then immediately derive context. Use current approval provenance, original activity/acceptance/rework summaries and verified dependency summaries. Read raw linked records only for a stated gap. Do not broadly enumerate or restart to recreate missing context.

Preserve the complete objective, mandatory deliverables and dependencies, current permissions, task/revision/approval, both owners, actual input/artifact versions, original run/host/mode/executor, handles, actual termination facts and unresolved evidence. A summary is neither approval nor execution evidence. Source hashes identify content; they do not establish authenticity or scientific correctness.

## Original work and end

An executing label, timeout, post-spawn error, kill failure or tool return does not prove the business writer ended. Keep the original observer/handle and identity; block a second writer until actual end is known. Submit does not stop or cancel a process. Direct child close does not prove detached descendants ended. Spawned CLI close saves process_observed and retains active identity. After actual related business activity ends, submit business-end-reference on that original run. Failed observation publication retains terminal facts and active identity for same-run recovery; never restart the host to recover a log. Never remove state, receipts or locks or start another run to bypass uncertainty.

After actual end, submit the original step/runId and complete current facts. A full same-run receipt can replay only with the original path/hash, complete bindings and all canonical caller facts/extensions unchanged. Reuse does not re-execute ended business work. Conflicts and partial finals remain preserved. A stale factual closure never restores approval or acceptance.

## Format and damaged contract

Only the current namespace is consumed. Unsupported records stay byte-for-byte in place; no conversion, default executor or inherited verified state is inferred. Already active tasks continue with the controller that began them under their existing approval and permissions; updating this skill does not replace an active controller. A separately preserved matching controller is used only for positively identified records under later explicit authorization, not as an automatic fallback.

Whole unknown/corrupt state blocks control writes and requires manual recovery. Preserve bytes, handles and diagnostics; do not ask another controller to guess damaged current state. In contrast, a complete current state and unique trusted begin remain the authority when the contract later breaks. status/context return the original identity with damage diagnostics and no new-work eligibility. New decision/begin/verify are blocked. Actual ended work may close only the matching original run as stale and acceptedForVerification=false. Restoring contract bytes alone does not revive approval.

## Drift, acceptance and rework

Input or reviewed-plan changes invalidate approval. Accepted evidence changes invalidate affected tasks and downstream dependencies; stale does not mean the original process ended. Inspect actual content, values, scientific claims, figures, links and instructions as well as digest identity. Preserve contradictory, negative and inconclusive findings.

Failed execution can retry within the still-valid method. Changed closed pending/verified/stale artifacts first require explicit rework with original run, receipt hash, reason/reference and requestId. Preserve prior attempts and accepted evidence; do not overwrite history. Trusted closed runs can be administratively reworked after approval loss or task/cache removal, without restoring approval. A missing or truncated acceptance cache is stale/recovery evidence, not a verified result. Material method/scope/input/permission/resource/acceptance changes need a complete new human review.

Acceptance failure retains original run and actual report/log/process facts, including multiple operation/state/journal/lock failures. For applicable review criteria obtain a fresh snapshot and actually re-read the bound content; preserve initial expected hashes through reading. A snapshot or exit0 has no semantic verdict. Repair declared failures before release and re-verify affected dependents under [runtime](runtime.md).

## Infeasible plans and stalled progress

For an infeasible plan, repeated critical-path stagnation or persistent blockage without a viable recovery route, follow [self-audit and complete replanning](replanning.md). Recover original goals, constraints, actual failures and still-applicable results; use the supported original-run and pending-result closure before revising live plans. Unknown activity or invalid approval may permit a separately prepared alternative, not a claim that runtime revision has succeeded. Normal waiting and isolated execution defects retain their ordinary recovery routes.

## Installation and ownership

Only a completed current installed transaction can start rollback after full target/configuration/directory/metadata/plan/backup preflight. Prepared, partial, rollback-prepared or unknown versions are diagnostic records, not automatic recovery permission. Keep actual restoration prefixes, unconfirmed writes, failed journal facts and backups. Unknown content or object identity blocks overwrite; no blind retry or automatic rollback of partial restoration.

Use [context and collaboration](context-hygiene.md) for role transfer or execution/verification/rework handoff. Confirm the old writer actually stopped, preserve original identity and grant only existing rights. The verifier is read-only and returns findings; the sole controller arranges rework and verify. Ordinary handoffs remain lightweight.

Do not create background daemons, schedules, cross-task memory or extra model processes to recover a task. Continue authorized independent mandatory work while one branch awaits a real decision or external change. Completion requires all mandatory acceptance; elapsed time or a fixed attempt count is not a completion criterion. Use [execution judgment](execution-judgment.md) to redirect when repeated attempts yield no new evidence.
